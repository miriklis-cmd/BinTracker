# BinTracker Database

## Activated logical movement lineage (normal schema17 runtime candidate)

BT-20-P2 makes the Task20D Data-owned coordinator the sole normal SQLite startup funnel. `Program` retains its ready session for the host lifetime; normal DI registers the native initial-lineage writer, Single receipt store, mutation writer and transactional projection authority only as part of this same cutover. The normal catalogue ends at17, while its schema17 callback fails closed because actual 16→17 execution requires the coordinator's ownership, preflight, verified backup, migration and postflight prerequisites. Explicit schema16 compatibility fixtures retain a separate catalogue ending16.

Developer Load/Fresh markers are no longer applied by a pre-DI file-copy/delete path. The coordinator exclusively claims the marker, validates its exact active and staged paths, executes coordinated replacement/fresh activation, restarts classification for the published physical identity, revalidates schema17 readiness, and only then completes the marker. The control state durably distinguishes execution-required, execution-in-progress and publication-ready-for-cleanup; only marker absence is fully completed. Each state update writes and flushes a complete sibling control file, then atomically replaces the marker under the claim lock, so an interrupted update retains a complete prior state rather than truncated JSON. A publication-ready marker retains the exact published physical identity, so re-entry revalidates that identity and finishes cleanup without another replacement; an interrupted execution fails recovery-required rather than replaying blindly. Other participants still observe the marker as a conflict; malformed, mismatched or unclaimable markers fail closed.

| Observed startup state | Coordinated action |
|---|---|
| Absent | Canonical parent/path bootstrap reservation; non-overwriting file creation; acquire physical upgrade ownership before baseline creation; release bootstrap reservation; build the supported baseline through16. Concurrent StartAsync participants wait for creator completion through a cancellation-aware named kernel mutex, then the losing call itself classifies the created database. The completion signal confers no database ownership and does not replace the physical lease/pin. An interrupted empty bootstrap is partial, not silently recreated. |
| Recognizable pre16 baseline | Exclusive physical maintenance ownership; existing numbered migrations through16; continue into activation under the same ownership. |
| Schema16 | Reject partial lineage tables/columns and malformed version state; preflight; verified non-overwriting backup; exact physical identity and complete persisted schema/value comparison with that backup; governed migration/backfill; strict transaction publication postflight; COMMIT17. |
| Native17 | No schema16 preflight, backup or migration prerequisites. Inspect required structural capabilities and existing current-root/projection health in one read snapshot. Initial and later native generations are valid. |
| Future schema | Typed rejection before EnsureCreated or schema/data mutation. |
| Partial/corrupt or unknown | Withhold readiness; report observed schema/identity where provable. No repair/restore guess. |

After migration, native validation precedes release/reacquisition of runtime ownership; exact identity, schema, capabilities and health are revalidated before readiness. Native re-entry also performs final validation under shared runtime ownership. The session retains its shared lease and physical-file pin until host shutdown. Failure returns a typed reason/phase and a fresh persisted observation; a post-COMMIT error, failed native validation or failed lease transition leaves committed17 reported as17. The migrator rolls back only before its successful COMMIT and preserves an original post-COMMIT exception. The complete persisted schema/value fingerprint is checked again inside its write transaction before the first schema17 DDL, closing the verification-to-mutation gap. Cancellation reports the fresh persisted state: precommit rollback16 or actual committed17. SchemaMutationAttempted records entry into schema mutation, separately from file replacement publication.

R5 compares tables, required column names/types/nullability, exact PK membership, composite FK columns/targets/update/delete actions, unique key columns/collations/order and filtered predicates, and tokenized required CHECK expressions from the shared schema17 DDL. It additionally checks shared-model base columns/types/nullability/PKs/unique keys/FKs and SQLite integrity. Token boundaries and quoted literals remain distinct; quoted NULL or multi-token constants cannot impersonate governed predicates. Schema16 activation and Load staging also validate base capabilities before proceeding. The in-memory structural reference contains no schema16 migration prerequisite or baseline history. Conservative predicate matching recognizes the governed constraint shapes; arbitrary rewritten equivalent predicates are not silently accepted. Existing native structural/current-root validation plus the unbounded operational projection run in the same snapshot, so Invalid/missing-current/orphan/unrooted ordinary evidence cannot produce readiness. MigrationBaseline-only checks remain confined to actual publication.

`LoadAsync`/`FreshAsync` use the same physical maintenance gate, prepare a provider-consistent replacement or fresh16 baseline under its own physical lease, checkpoint WAL with closed SQLite handles, preserve the old database under a unique name and replace atomically while both physical identities remain owned. Load into an absent target uses bootstrap reservation. After replacement every OLD schema/preflight/backup/identity assumption is discarded. The NEW published physical identity is retained as the expected identity through startup acquisition and final native validation. A competing replacement during the ownership-release gap causes IdentityChanged; Load/Fresh cannot return readiness for that later file. The stable staged copy is classified and validated before swap: native17 uses structural/current/projection checks; schema16 uses base capabilities and migration preflight. Invalid/future sources leave the selected old target unchanged. Failures before swap retain staged evidence and the old identity; failures after swap report DatabaseReplacementPublished and the new selected state, preserving the old file without auto-restore. Source copying uses SQLite BackupDatabase under runtime identity ownership; both target and stage retain exclusive physical leases across the swap. BT-20-P2 connects these APIs to the normal developer restart marker without a second replacement authority.

R4's single Data-owned startup funnel covers absent, pre16, schema16, schema17, future-schema and developer replacement paths. Creation uses a path/bootstrap reservation only until physical identity exists; existing databases use physical-identity coordination. Existing17 startup validates native capabilities/current health without schema16 preflight or a retained migration backup. Schema16 migration still requires exclusive ownership, classification, preflight, verified non-overwriting exact-source backup/equivalence, strict transactional publication postflight and native health. Lease transition/reacquisition revalidates exact identity/schema/health before activated host composition. A postcommit failure cannot claim schema16 rollback. Developer Load/Fresh stays coordinated and restarts classification after identity replacement; no fake conflict bypass is permitted.

R5 structural capability proof includes tables/columns/PK/FK/RESTRICT/unique indexes/relevant CHECKs as well as current generations and relevant orphan/unrooted ordinary evidence, using the existing validator/projection. R6 companion leases only coordinate participating clients; stopped old/nonparticipating clients are a later rehearsal/deployment prerequisite. Task20E adds R1's typed Single receipt to schema17: immutable command-response evidence only, never balance/projection/lineage/report/audit authority, and never backfilled for legacy entries. BT-20-P1 aligns EF tracking with immutable membership through `ClientNoAction`: deleting a loaded schema17 batch leaves the dependent identity intact before the persisted RESTRICT failure. Data keeps catalogue semantics explicit: fresh/current schema16 retains accepted persisted `SET NULL`, while schema17 validation requires `RESTRICT/NO ACTION`. Native audit classification reads the complete persisted request/version/root/expected/result envelope plus generation association; any native indicator requires the complete valid native shape before affected-root validation. Migrated alpha.8 operations remain legacy only when all native envelope fields are null and no generation references the operation; a root association alone does not invent native semantics.

The logical-lineage migration is permanently allocated as **schema 16 -> schema 17** and is governed by BT-CORR-018..033, BT-AUD-015..017 and BT-OPS-011..012. The normal coordinator invokes deterministic schema16 backfill and transaction-bound postflight only after read-only preflight, exclusive ownership and verified exact-source backup. Migration publication proves the frozen generation-zero `MigrationBaseline` shape. Schema17 re-entry separately checks structure, FKs, ownership/introduction completeness and every projectable current root without imposing migration-only predicates on native `Initial` or later generations. The resolver materializes one requested current generation under one SQLite read transaction and applies provider-neutral validation before returning immutable success models. The production DbContext deliberately does not map lineage entities; Data-owned native SQL is the provider adapter. The normal catalogue ends at17, while explicit schema16 compatibility uses a separate baseline catalogue ending16.

The infrastructure-internal planning materializer extends that exact CURRENT snapshot with get-only immutable movement facts, including persisted `ReversesMovementId`. Before returning a trusted planning snapshot it rejects a Reversed pair unless the terminal row reverses the exact LastEffective ID, is the opposite direction with equal customer/container/quantity, has `MovementSource.Manual`, and has null `ImportRunId` and `MovementBatchId`. The pure planner independently rechecks those facts and rejects a LastEffective or TerminalReversal `MovementDate` after its separate authoritative business date; Active current effective dates receive the same future-date check. This is current-pair validation only, not a full-chain forensic scan or runtime activation.

Normal schema17 composition selects the SQLite initial-lineage writer; explicit schema16/no-Data compatibility composition retains the dormant writer that performs no schema probe, query or write. The existing provider-neutral `MovementService` remains the Single/Batch business authority and invokes the native writer inside its existing transaction only after authoritative validation and physical persistence have established the successful request. The schema17 writer rejects incompatible or unhealthy schema state before a new physical write can commit. It constructs one `Initializing` root, generation 0 of kind/action `Initial`, one permanent logical line and RootOriginal ledger link per original physical movement, then fills same-line introduction pointers, validates the construction-only graph plus existing schema17 structural/current health, and activates the root with `CurrentGenerationNumber=0`. No `Initializing` root or null `IntroducedByGenerationLineId` may commit. Single uses ordinal 0; Batch preserves first-successful request enumeration order. Generated movement IDs are never ordering authority.

Generation zero creates neither a `MovementCorrectionOperation` nor a `LogicalMovementPhysicalOutput`. Existing `MOVEMENT_RECORDED` / `MOVEMENT_BATCH_RECORDED` audit actions remain. Equivalent retries preserve committed command identity without rewriting ordinals or lineage, including reordered Batch retries; migrated schema16 roots retain `MigrationBaseline` rather than becoming `Initial`. Batch exact-result replay is unchanged. In the normal native17 Single path, physical evidence, Initial lineage, the transaction-participating PositionAsOf projection, one typed receipt and audit share the caller transaction. Receipt and audit persist the same checked signed projection result; first success returns that persisted typed evidence, exact native retry reads it without projection, and migrated/pre-receipt retry returns the typed controlled unavailable outcome without synthetic receipt. Projection, lineage, receipt, cancellation, overflow or audit failure before commit rolls back every new artifact. Explicit schema16 Single retains its compatibility calculation. These SQLite mechanics remain confined to Data, while the receipt concept and construction invariants are provider-neutral in Core and workflow semantics remain client/provider-neutral above Data. The production DbContext still does not map lineage entities; no PostgreSQL provider, API or additional client is implemented by this slice.

Normal schema17 mutation composition persists planned Correct/Reverse/Restore operations atomically with complete next-generation state, movement/ledger evidence, optional physical output and one primary AuditEvent. Provider-owned selection lookups resolve persisted movement/batch anchors to the stable logical root inside the caller's read transaction; Services maps the trusted snapshot to client-neutral preview data. Generation-line identities come only from `LogicalMovementGenerationLines.Id`. Execution retains preview `ExpectedGeneration`; Active-only whole-root policy blocks any Reversed line until later UI. After rollback, provider conflicts use fresh committed evidence for replay/conflict/stale ordering. Enabled native17 composition rejects all alpha.8 correction/reversal writes; only explicit schema16 compatibility composition retains them.

The normal SQLite corrected-projection authority uses one serializable read transaction to capture logical roots, influence identities, ownership/introduction links, movement facts and ImportRun identities; relevant roots are resolved and cross-validated in that snapshot before Core projects contributions and aggregates signed positions. Candidate selection considers every structurally owned movement/root/generation pointer before final filters. Missing or malformed facts widen relevance and fail closed unless a known dimension proves disjointness. Manual/Batch evidence must be owned exactly once; Adjustment and ExcelImport remain separate and are unioned once. Normal consumers never fall back to raw arithmetic after projection failure.

The normal Import comparison/execution consumer uses one inclusive `PositionAsOf(CutoverDate - 1 day)` result for replacement when that date exists and subtracts any selected previous ImportRun-owned pre-cutover rows by persisted customer/container identity and signed physical effect exactly once. The minimum `DateOnly` cutover has no earlier representable date and therefore an empty replacement baseline. Ordinary new-import execution instead uses `PositionAsOf(DateOnly.MaxValue)` to preserve its accepted all-representable-dates whole-ledger baseline. A transaction-participation contract lets the same SQLite projection implementation consume the caller-owned serializable execution transaction without creating or committing another transaction; eligibility, projection, deletion and all import writes therefore share one snapshot/transaction. Failure and cancellation leave no import write and never fall back to raw arithmetic. Explicit schema16 compatibility comparison/execution retains its legacy path.

The migration-safety infrastructure is active in the normal startup funnel. A Windows physical-file-identity-scoped shared/exclusive companion lease gives every normal participating process a shared runtime lease for its selected database, while upgrade/recovery takes the exclusive lease across preflight, backup, comparison, migration and postflight. It remains per database rather than making BinTracker globally single-instance, coordinates pending developer operations through the same coordinator, and releases on handle disposal or process death. Read-only SQLite preflight uses persisted tables/IDs/FKs/correction/reversal relationships only and returns stable classifications/reasons plus structural and exact table-count fingerprints.

The production pre-lineage backup destination is `%LOCALAPPDATA%\BinTracker-RecoveryPreUpgrade`; this artifact family is outside ordinary `BackupRetentionCount` cleanup and is never automatically deleted in v1. Each backup is published without overwrite as `BinTracker-pre-lineage-v<schema>-<yyyyMMddTHHmmssfffZ>-<short-guid>.db`. The migration-grade service uses SQLite `BackupDatabase`, requires a non-empty result, verifies source/backup preflight equivalence, integrity/FKs/schema/counts, and writes a versioned recovery manifest plus adjacent checksum evidence covering both the database and manifest. The manifest records artifact/purpose/provider/application/source identity/schema/size/timestamp/journal-mode facts, backup size/hash, exact counts, preflight classification/fingerprint and the recovery-policy identifier/instructions. Recovery verification is bound to the expected active database by canonical path, path hash, Windows physical file identity and expected schema. Recovery classification preserves a valid rolled-back source and permits controlled restore only when the active database is unusable and the fully verified backup belongs to that exact source. Normal schema16 activation now invokes the verified backup path before mutation; retained-production-database rehearsal and stopped-client recovery remain pending.

- `LogicalMovementBatch`: stable root, nullable unique RootMovementBatchId as sole original physical-batch link, CurrentGenerationNumber, status/reason and line count.
- `LogicalMovementLine`: one root, immutable RootMovementId and immutable OriginalDisplayOrdinal; no current pointer.
- `LogicalMovementGeneration`: unique root/generation number, predecessor, operation, kind/count/time.
- `LogicalMovementGenerationLine`: one row per permanent line per generation, explicit action/state/AppliedFieldMask, predecessor and Active or Reversed movement pointers; no authoritative before/result JSON.
- `LogicalMovementLedgerLink`: one movement owner/line and transformation role. IntroducedByGenerationLineId may be null only during transaction construction/backfill and must be filled before Active or ReadOnly commit.
- `LogicalMovementPhysicalOutput`: output-only association for a physical correction-output `MovementBatch`; schema 17 can identify the logical root and exactly one logical generation or uniquely proven legacy correction operation. It never duplicates `RootMovementBatchId` or represents the original physical batch. The schema-16 -> 17 MigrationBaseline deliberately creates no rows for historical correction-output batches; their existing `MovementCorrectionOperations.ReplacementBatchId`, `MovementBatch` header and exact `BinMovement.MovementBatchId` membership remain forensic evidence. After lineage activation, every newly created truthful correction-output batch must have exactly one generation-linked row, and each generation/output batch can occur at most once.
- `SingleMovementResponseReceipt`: one immutable typed native Single response keyed by ClientOperationId, uniquely bound to its physical MovementId with RESTRICT deletion, and containing the captured business date plus checked signed resulting position. Schema16 migration creates no rows. It is replay evidence only and is never queried for current position, lineage, reports or audit reconstruction.
- existing `MovementCorrectionOperations` remains the storage-compatible movement-change operation/idempotency envelope and gains logical root/expected/result generation plus canonical versioned request/fingerprint. Its persisted `Kind` values are permanently allocated as `Single=0`, `WholeBatch=1`, `Reverse=2`, `Restore=3`; 0/1 retain their existing meanings and no value may be renumbered without an explicit data migration.
- existing `MovementCorrectionLines` remains legacy correction-triple forensic/compatibility evidence only and is not populated as a competing authority for new logical generations.
- `AuditEvents` gains nullable unique `MovementCorrectionOperationId` with a RESTRICT/NO ACTION FK to the operation envelope. Historical rows may remain null under the deterministic legacy-association rule; every new logical mutation later requires one primary event in the same transaction. Audit health remains separate from operational state.
- Under explicit native17 composition, audit detail/review reads that persisted association in the caller transaction, checks the associated root through the existing operation-audit health validator, and returns a controlled no-detail result for healthy native evidence until the later full native detail UI. Logical-root and physical-movement identity domains are never substituted; action/payload text cannot select native lineage authority.

Portable PK/FK/RESTRICT/UNIQUE/CHECK/index constraints and root CAS combine with transactional service/validator cardinality checks; no SQLite triggers/deferred-FK dependency. Persisted batches/movements/evidence use RESTRICT/NO ACTION rather than ordinary detach/delete.

### Schema-16 -> 17 migration-population contract

Schema capability, baseline population, lineage-native writes and retained legacy evidence are distinct. `MIGRATION-REQUIRED` means a deterministic value must be present before a migrated Active/ReadOnly root commits. `LEGACY-NULL / NEW-WRITES-ONLY` means migration preserves the old row but intentionally leaves the new field null. `CONDITIONAL-STRUCTURAL` permits population only from the stated unique persisted-ID proof. `NOT-APPLICABLE-TO-LEGACY` means the concept describes a later lineage-native operation, not MigrationBaseline.

| Structure / field | Classification and schema-16 -> 17 action | Lineage-native / legacy rule |
|---|---|---|
| `LogicalMovementBatch.RootMovementBatchId` | `MIGRATION-REQUIRED` for a physical-origin root from exact original batch membership; null for a proven single-entry root. | Sole original physical-batch authority. New Batch Entry supplies it; new Single Entry leaves it null. |
| root `Status`, `CurrentGenerationNumber`, `LineCount`, `StatusReasonCode`, `CreatedUtc` | `MIGRATION-REQUIRED`: derive status/reason from preflight classification, use generation 0 as current for Active/ReadOnly, persist exact permanent-line count, and use migration execution UTC as metadata creation time. Active normally has no reason; ReadOnly/Invalid carries a stable reason. | Initializing is construction-only. Invalid must not receive a fabricated reportable current pointer; it may retain only a separately validated diagnostic pointer. |
| `LogicalMovementLine` root, `RootMovementId`, `OriginalDisplayOrdinal`, `CreatedUtc` | `MIGRATION-REQUIRED`: create one line per proven original ordinary line, ordinal zero-based by ascending RootMovementId, with migration execution UTC. | RootMovementId is identity; ordinal is immutable presentation metadata only. |
| `LogicalMovementGeneration` root, number, kind, count, time | `MIGRATION-REQUIRED`: one full generation 0 of kind MigrationBaseline, exact line count and migration execution UTC for each Active/ReadOnly root. | New roots use Initial; later substantive changes use the applicable lineage-native generation/action semantics. |

For Active and ReadOnly, successful migration requires a complete current generation, exact line count, valid state-pointer shape, complete movement ownership/roles and non-null introduction links. ReadOnly differs only because mutation history/safety is unsupported; its current projection is still proven. Invalid is used when current projection or ownership cannot be proven and must not be padded with invented rows/pointers to satisfy Active/ReadOnly constraints. Initializing must not survive a successful migration transaction.

Numeric projection uses one connection/context and read transaction in SQLite WAL; validation and aggregation share that snapshot. Future PostgreSQL uses equivalent read-only repeatable snapshot semantics behind infrastructure.

Print Pack report participation is internal to Services/Data composition. The public Outstanding and Daily report interfaces expose only `QueryAsync` with query/result DTOs; their internal snapshot participant interfaces are explicitly implemented by the existing report classes. Neither EF context nor transaction/provider types cross the application-facing report contract. SQLite implements the snapshot today; a future suitable SQL provider must supply equivalent consistency without changing client contracts or report business semantics.

The normal Daily Print Pack shared-read boundary is implemented by `ITransactionalOperationalMovementProjectionAuthority.ReadSnapshotAsync`. The SQLite adapter requires a caller-owned context with no existing transaction, opens/enlists one deferred Serializable transaction, awaits the callback, and disposes its own transaction/enlistment on success, failure or cancellation. It never saves/commits and preserves caller context/connection ownership. The first read fixes the database snapshot; WAL writers may commit while the reader continues seeing its original state. Both report projection queries use the existing `QueryInTransactionAsync` machinery, and EF customer/container lookups use the same transaction. The callback must perform sequential awaited reads and return materialized results, without writes or transaction replacement. Existing caller-owned write transactions still use `QueryInTransactionAsync` directly; the snapshot owner rejects nesting rather than taking ownership of an import transaction. Explicit schema16 compatibility retains independent delegated reads.
