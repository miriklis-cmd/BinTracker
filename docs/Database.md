# BinTracker Database

## Dormant logical movement lineage (schema 17 migration, current-root resolver and trusted planning materializer implemented for isolated tests; not activated)

The logical-lineage migration is permanently allocated as **schema 16 -> schema 17** and is governed by BT-CORR-018..033, BT-AUD-015..017 and BT-OPS-011..012. Dormant schema-17 DDL, deterministic schema-16 backfill, transaction-bound postflight validation and a validation-gated CURRENT-root resolver are implemented behind explicit APIs for isolated tests. The resolver materializes one requested root and the generation selected by `CurrentGenerationNumber` under one SQLite read transaction, then applies provider-neutral validation before returning non-publicly-constructible immutable success models. It proves RootOriginal/current pointer links and introductions, exact original physical-batch/null-single membership, unique non-negative presentation ordinals, and preserves `StatusReasonCode`; unrelated historical-only links remain migration/diagnostic scope. It deliberately does not scan historical generations. The production DbContext does not register lineage entities, the active startup migration catalogue still ends at schema 16, and normal startup neither creates nor migrates to schema 17. No production consumer uses the resolver; activation remains later.

The infrastructure-internal planning materializer extends that exact CURRENT snapshot with get-only immutable movement facts, including persisted `ReversesMovementId`. Before returning a trusted planning snapshot it rejects a Reversed pair unless the terminal row reverses the exact LastEffective ID, is the opposite direction with equal customer/container/quantity, has `MovementSource.Manual`, and has null `ImportRunId` and `MovementBatchId`. The pure planner independently rechecks those facts and rejects a LastEffective or TerminalReversal `MovementDate` after its separate authoritative business date; Active current effective dates receive the same future-date check. This is current-pair validation only, not a full-chain forensic scan or runtime activation.

The first migration-safety infrastructure is implemented but deliberately unactivated. A Windows physical-file-identity-scoped shared/exclusive companion lease provides the future preflight-to-postflight gate: every normal participating process will hold a shared runtime lease for its selected database, while upgrade/recovery holds the exclusive lease across preflight, backup, comparison, migration and postflight. It remains per database rather than making BinTracker globally single-instance, checks the pending-operation marker before granting upgrade ownership, and releases on handle disposal or process death. Read-only SQLite preflight uses persisted tables/IDs/FKs/correction/reversal relationships only and returns stable classifications/reasons plus structural and exact table-count fingerprints.

The production pre-lineage backup destination is `%LOCALAPPDATA%\BinTracker-RecoveryPreUpgrade`; this artifact family is outside ordinary `BackupRetentionCount` cleanup and is never automatically deleted in v1. Each backup is published without overwrite as `BinTracker-pre-lineage-v<schema>-<yyyyMMddTHHmmssfffZ>-<short-guid>.db`. The migration-grade service uses SQLite `BackupDatabase`, requires a non-empty result, verifies source/backup preflight equivalence, integrity/FKs/schema/counts, and writes a versioned recovery manifest plus adjacent checksum evidence covering both the database and manifest. The manifest records artifact/purpose/provider/application/source identity/schema/size/timestamp/journal-mode facts, backup size/hash, exact counts, preflight classification/fingerprint and the recovery-policy identifier/instructions. Recovery verification is bound to the expected active database by canonical path, path hash, Windows physical file identity and expected schema. Recovery classification preserves a valid rolled-back source and permits controlled restore only when the active database is unusable and the fully verified backup belongs to that exact source. None of this is registered in startup, changes schema version 16, or runs against a production database yet.

- `LogicalMovementBatch`: stable root, nullable unique RootMovementBatchId as sole original physical-batch link, CurrentGenerationNumber, status/reason and line count.
- `LogicalMovementLine`: one root, immutable RootMovementId and immutable OriginalDisplayOrdinal; no current pointer.
- `LogicalMovementGeneration`: unique root/generation number, predecessor, operation, kind/count/time.
- `LogicalMovementGenerationLine`: one row per permanent line per generation, explicit action/state/AppliedFieldMask, predecessor and Active or Reversed movement pointers; no authoritative before/result JSON.
- `LogicalMovementLedgerLink`: one movement owner/line and transformation role. IntroducedByGenerationLineId may be null only during transaction construction/backfill and must be filled before Active or ReadOnly commit.
- `LogicalMovementPhysicalOutput`: output-only association for a physical correction-output `MovementBatch`; schema 17 can identify the logical root and exactly one logical generation or uniquely proven legacy correction operation. It never duplicates `RootMovementBatchId` or represents the original physical batch. The schema-16 -> 17 MigrationBaseline deliberately creates no rows for historical correction-output batches; their existing `MovementCorrectionOperations.ReplacementBatchId`, `MovementBatch` header and exact `BinMovement.MovementBatchId` membership remain forensic evidence. After lineage activation, every newly created truthful correction-output batch must have exactly one generation-linked row, and each generation/output batch can occur at most once.
- existing `MovementCorrectionOperations` remains the storage-compatible movement-change operation/idempotency envelope and gains logical root/expected/result generation plus canonical versioned request/fingerprint. Its persisted `Kind` values are permanently allocated as `Single=0`, `WholeBatch=1`, `Reverse=2`, `Restore=3`; 0/1 retain their existing meanings and no value may be renumbered without an explicit data migration.
- existing `MovementCorrectionLines` remains legacy correction-triple forensic/compatibility evidence only and is not populated as a competing authority for new logical generations.
- `AuditEvents` gains nullable unique `MovementCorrectionOperationId` with a RESTRICT/NO ACTION FK to the operation envelope. Historical rows may remain null under the deterministic legacy-association rule; every new logical mutation later requires one primary event in the same transaction. Audit health remains separate from operational state.

Portable PK/FK/RESTRICT/UNIQUE/CHECK/index constraints and root CAS combine with transactional service/validator cardinality checks; no SQLite triggers/deferred-FK dependency. Persisted batches/movements/evidence use RESTRICT/NO ACTION rather than ordinary detach/delete.

Persisted lineage enum values are permanent:

| Contract | Values |
|---|---|
| `MovementCorrectionKind` | `Single=0`, `WholeBatch=1`, `Reverse=2`, `Restore=3` |
| `LogicalMovementBatchStatus` | `Initializing=0`, `Active=1`, `ReadOnly=2`, `Invalid=3` |
| `LogicalMovementLineState` | `Active=0`, `Reversed=1` |
| `LogicalMovementGenerationAction` | `Initial=0`, `MigrationBaseline=1`, `CarriedForward=2`, `AlreadyMatches=3`, `Corrected=4`, `Reversed=5`, `Restored=6`, `RemainReversed=7` |
| `LogicalMovementTransformationRole` | `RootOriginal=0`, `CorrectionNeutraliser=1`, `CorrectionReplacement=2`, `OrdinaryReversal=3`, `Restoration=4` |
| `MovementChangeField` flags | `None=0`, `MovementDate=1`, `Direction=2`, `Customer=4`, `ContainerType=8`, `Quantity=16`, `Reference=32`, `Notes=64` |

`MovementSource` remains provenance and does not gain `MovementSource.Correction`. `LogicalMovementLedgerLink.IntroducedByGenerationLineId` may be null only while a transaction constructs/backfills the insertion cycle and must be populated before an Active or ReadOnly operational state commits. Generation lines store structured state/action/pointers and field mask, never authoritative before/result JSON.

`AppliedFieldMask` is the exact line-level explicit override selection that governed the requested resulting business state, whether or not normalized values differ. Initial/MigrationBaseline/CarriedForward/Reversed/RemainReversed require `None`; AlreadyMatches/Corrected require the exact nonempty canonical correction selection; Restored requires the exact canonical restoration-override selection and permits `None`. Undefined bits outside `0..127`, missing/extra request bits, nonzero masks on no-override actions and action/state/request-version mismatches fail closed. The mask does not duplicate RequestJson intent, determine contribution, or establish no-op/movement/physical-output semantics.

Migration creates Generation 0 MigrationBaseline only from deterministic IDs/FKs/correction/reversal relationships. Status is Initializing, Active, ReadOnly or Invalid. Import-owned data is not grouped into generic roots. In a schema-16 source, MovementCorrectionOperations.Kind values other than historical Single=0/WholeBatch=1 are a database-wide migration blocker; they are never treated as ReadOnly and never acquire schema-17 Reverse/Restore meaning. Read-only preflight and verified recoverable backup are blocking before schema mutation.

### Schema-16 -> 17 migration-population contract

Schema capability, baseline population, lineage-native writes and retained legacy evidence are distinct. `MIGRATION-REQUIRED` means a deterministic value must be present before a migrated Active/ReadOnly root commits. `LEGACY-NULL / NEW-WRITES-ONLY` means migration preserves the old row but intentionally leaves the new field null. `CONDITIONAL-STRUCTURAL` permits population only from the stated unique persisted-ID proof. `NOT-APPLICABLE-TO-LEGACY` means the concept describes a later lineage-native operation, not MigrationBaseline.

| Structure / field | Classification and schema-16 -> 17 action | Lineage-native / legacy rule |
|---|---|---|
| `LogicalMovementBatch.RootMovementBatchId` | `MIGRATION-REQUIRED` for a physical-origin root from exact original batch membership; null for a proven single-entry root. | Sole original physical-batch authority. New Batch Entry supplies it; new Single Entry leaves it null. |
| root `Status`, `CurrentGenerationNumber`, `LineCount`, `StatusReasonCode`, `CreatedUtc` | `MIGRATION-REQUIRED`: derive status/reason from preflight classification, use generation 0 as current for Active/ReadOnly, persist exact permanent-line count, and use migration execution UTC as metadata creation time. Active normally has no reason; ReadOnly/Invalid carries a stable reason. | Initializing is construction-only. Invalid must not receive a fabricated reportable current pointer; it may retain only a separately validated diagnostic pointer. |
| `LogicalMovementLine` root, `RootMovementId`, `OriginalDisplayOrdinal`, `CreatedUtc` | `MIGRATION-REQUIRED`: create one line per proven original ordinary line, ordinal zero-based by ascending RootMovementId, with migration execution UTC. | RootMovementId is identity; ordinal is immutable presentation metadata only. |
| `LogicalMovementGeneration` root, number, kind, count, time | `MIGRATION-REQUIRED`: one full generation 0 of kind MigrationBaseline, exact line count and migration execution UTC for each Active/ReadOnly root. | New roots use Initial; later substantive changes use the applicable lineage-native generation/action semantics. |
| generation predecessor and operation relation | `NOT-APPLICABLE-TO-LEGACY`: Generation 0 has null predecessor and null movement-change operation. | Later generations reference N-1 and exactly their committing movement-change operation. A legacy operation never becomes the creator of MigrationBaseline. |
| `LogicalMovementGenerationLine` root/generation/line, state, action, mask, pointers, time | `MIGRATION-REQUIRED`: exactly one MigrationBaseline row per permanent line; `AppliedFieldMask=None`; Active has ResultEffectiveMovement only; Reversed has LastEffectiveMovement plus TerminalReversalMovement; use migration execution UTC. | New generations use their real action/mask/pointer shape. No before/result JSON is state authority. |
| `PreviousGenerationLineId` | `NOT-APPLICABLE-TO-LEGACY`: null on MigrationBaseline. | Every later generation line points to the immediately preceding state row for that logical line. |
| `LogicalMovementLedgerLink` movement/root/line/role/time | `MIGRATION-REQUIRED` for every structurally owned ordinary original, correction neutraliser/replacement and ordinary reversal in an Active/ReadOnly component; use migration execution UTC. | One immutable movement owner and role. Import/Adjustment evidence remains outside generic lineage. |
| `IntroducedByGenerationLineId` | `MIGRATION-REQUIRED`: after inserting the baseline state, point every migrated link to that line's MigrationBaseline generation-line row before Active/ReadOnly commits. | This means “introduced into the logical-lineage model by this baseline”, not “the historical movement was created by generation 0”. Null is transaction/backfill-temporary only. |
| ledger-link legacy correction-line association | `CONDITIONAL-STRUCTURAL`: set only for an exact unique `MovementCorrectionLine` role relationship; otherwise null without guessing. | It is compatibility evidence, never current-state or transformation authority. |
| `LogicalMovementPhysicalOutput.MovementBatchId`, root, `GenerationId`, `LegacyMovementCorrectionOperationId`, `CreatedUtc` | `NOT-APPLICABLE-TO-LEGACY` for the schema-16 -> 17 MigrationBaseline: create no row, so none of these fields is populated for the seven or any other historical correction-output batches. | Schema retains exact batch/root identity and exactly one of generation/uniquely-proven-legacy-operation. Every new truthful lineage-native output requires a generation-linked row with creation UTC. Any later legacy conversion requires a separately authorized deterministic process and must not imply a fabricated generation. |
| legacy operation `ClientOperationId`, `RequestFingerprint`, `Kind`, `OriginalBatchId`, `ReplacementBatchId` | `MIGRATION-REQUIRED` preservation: copy existing values and relationships unchanged through any table rebuild. | They remain persisted idempotency/forensic evidence. `ReplacementBatchId` remains the authoritative legacy output association when no PhysicalOutput row is backfilled. |
| legacy operation `LogicalMovementBatchId` | `CONDITIONAL-STRUCTURAL`: populate only when correction lines/batch relationships prove exactly one migrated root; otherwise null with the root's migration classification/reason. | New movement-change operations always identify their root. Root association does not claim a historical generation. |
| legacy operation `RequestJson`, `RequestSchemaVersion`, `ExpectedGenerationNumber`, `ResultGenerationNumber` | `LEGACY-NULL / NEW-WRITES-ONLY`: leave null; exact historical intent and logical-generation numbers did not exist and are not reconstructed. | New operations require canonical request/schema and expected/result generations. No global cross-domain ClientOperationId namespace is introduced. |
| separate operation target-line relationship | `NOT-APPLICABLE-TO-LEGACY`: no separate target-line FK is frozen or backfilled; legacy `MovementCorrectionLines` remain the structural correction triples. | New targeted intent/result is represented by the canonical operation request and affected full generation lines, not a competing authority. |
| `AuditEvent.MovementCorrectionOperationId` | `CONDITIONAL-STRUCTURAL`: populate only when BT-AUD-017 proves exactly one complete structured-ID match; otherwise leave null and record the stable unlinked-legacy-audit diagnostic. | Every new lineage mutation requires exactly one primary operation-linked audit in its transaction. No prose/time/value inference or synthesized audit. |
| existing `BinMovement.MovementBatchId` membership | `MIGRATION-REQUIRED` preservation: retain every exact membership while rebuilding its FK from `SET NULL` to `RESTRICT/NO ACTION` in schema 17. | Ordinary deletion cannot detach immutable physical evidence. Import Replace/Correct deletes ImportRun-owned movements, not MovementBatch rows; regression tests must cover that governed exception and developer whole-database reset. |

For Active and ReadOnly, successful migration requires a complete current generation, exact line count, valid state-pointer shape, complete movement ownership/roles and non-null introduction links. ReadOnly differs only because mutation history/safety is unsupported; its current projection is still proven. Invalid is used when current projection or ownership cannot be proven and must not be padded with invented rows/pointers to satisfy Active/ReadOnly constraints. Initializing must not survive a successful migration transaction.

The inspected schema-16 evidence (495 movements, 30 batches, 10 correction operations, 17 correction triples, 7 ordinary reversals, 7 historical correction-output batches and 28 deterministic ordinary roots) maps to 28 Active roots with generation 0/full lines and structurally owned ledger links. Batch #30 becomes one complete baseline with its active line and its reversed line. The 10 operations retain existing evidence and receive a root ID only where uniquely proven; request/generation fields remain null. Strong uniquely matched legacy audits receive the operation FK. The seven historical output batches receive no `LogicalMovementPhysicalOutput` rows and remain evidenced by `ReplacementBatchId` plus physical membership. This evidence is a rehearsal shape only; every real database repeats read-only preflight immediately before migration.

Numeric projection uses one connection/context and read transaction in SQLite WAL; validation and aggregation share that snapshot. Future PostgreSQL uses equivalent read-only repeatable snapshot semantics behind infrastructure.

## Schema V16 movement corrections and review

V16 adds `MovementCorrectionOperations` and `MovementCorrectionLines` with unique client-operation and original/neutraliser/replacement lineage indexes. The existing unique `BinMovements.ReversesMovementId` remains the cross-command arbiter. Audit review columns default to false/null so historical reversal events do not become newly pending after upgrade.

## Schema V14 concurrency foundation

V14 adds optimistic `Revision` tokens, normalized unique Container Type `NameKey`, persisted operation IDs, provenance-only `SourceClientPath`, nullable unique `ImportRun.CurrentCutoverDate`, and import `ClientRequestFingerprint`. SQLite migration SQL remains isolated in Data; PostgreSQL requires its own provider migrations and real integration fixture.

## ApplicationSettings business information

The singleton `ApplicationSettings` row also stores configurable Business Information:

- BusinessName
- TradingName
- Abn
- Address
- Phone
- Email
- DefaultReportHeader

Schema migration v8 adds these columns to existing SQLite databases without replacing the settings row.


## Branding schema status

The current schema stores textual Business Information only. There is no logo/blob/path field yet. Logo persistence and migration design are part of the pre-v1 Business Information & Branding milestone and must be decided before schema implementation.
